## 你的分工（先读，省时间）

**启动你的那个包装脚本 `tools/run-daily.ps1` 运行在沙箱外，它负责构建和推送。你做它做不了的部分。**

实测结论（不是推断，是真跑出来的）：

| 操作 | 沙箱内（你） | 包装脚本（沙箱外） |
| --- | --- | --- |
| `astro build` | ✗ 报 `require is not defined` | **✓ 36 页** |
| `git ls-remote` / `git push` | ✗ 报 `couldn't create signal pipe, Win32 error 5` | **✓ 推得出去** |

**所以**：

- **不要**去修 `astro build`、不要去修 git remote、不要换构建命令、不要清缓存、**不要因为 preflight 报 BLOCKING 就停下**。
- **你写完直接本地 commit。** 包装脚本会在你结束后：**跑 preflight → 跑构建（不过就不推）→ 推送 → 等部署 → 核实线上**。
- `preflight` 在你这里会报若干 BLOCKING，**其中构建、git remote、python 是沙箱产物，不是你造成的**。看其余项（`qa-check`、`tools parse`、`review-dates`）即可。

## 第三步：这一轮做什么

**核心循环**（做法 C：不依赖外部、先提升已有质量）：

```
1. 取 reviewBy 最近到期的一篇
2. 对照它引用的一手来源重读（读原文，不读二手转述）
3. 有实质变化 → 公开更正（写进 frontmatter 的 revisions 与 updatedDate）
   无实质变化 → 明确记录「无需改动」，绝不只改日期
4. 跑闸门 → 本地 commit
```

**栏目轮换**：每栏目每周 1–3 篇。

开工先查本周哪个栏目是 0 篇（`指令_完整版.md` 里有那段命令）。**一周里某栏目一篇都没有，那不是轮换，是断更。**

- 最近到期的文章有实质改动 → 先更正它
- 若不需要改动，而某栏目本周是 0 篇 → **写一篇那个栏目的新文章**
- 两件都需要 → 都做

**写新文章时优先只用仓库里已核实的数字**（不读新文件），那样最省。要写新事实时才读一次文献。

**编号**：新文章取当前 `articleNumber` 最大值 +1，写进 frontmatter。

## 第四步：硬性要求（违反任何一条都不得发布）

- frontmatter 长度：`title` ≤120、`subtitle` ≤160、`description` ≤300 字符。**超一个字符整个构建会失败，全站页面会掉回上一次部署。**
- `figures` ≥5 条，每条必须有 `value` / `unit` / `period` / `source` / `retrieved` 五项。
- `sources` ≥3 条，必须是一次文献（法规、公报、海关公告、Federal Register、EUR-Lex 等），不是二手报道。
- 正文至少一个带金额的每件/每柜/每吨成本表，且**必须调 `tools/` 里的模型**，不许即兴算术。
- 禁止模糊词：`may` / `might` / `possibly` / `perhaps` / `could` / `reportedly` / `allegedly`（月份 `May` 首字母大写不受限）。
- `AI Summary` **必须恰好 40–60 词**。
- 必须有 `## How we calculated this`，把算式写出来。
- 每篇至少 1 条对外正文内链，**且不得形成 A→B 与 B→A 的环形对**。
- 每个数字都要能追到来源；查不到就写「查不到」，**不要编**。
- **不要写第一人称体验**（"I have run this play twice"），零人工审稿下那只能是编的。

## 第五步：交付（你负责到本地 commit 为止）

```

node tools/serp-check.mjs <文件> --serp=file:data/serp/<文章名>.json
node tools/reviewer-check.mjs --all
node tools/link-check.mjs
git add -A && git commit
```

**推送、构建验证、线上核实由包装脚本接手。** 你只要保证本地 commit 是干净的。

`node tools/feishu-sync.mjs` 你也可以跑（走网络 API，不走命名管道）。

最后更新 `进度日志.md`。

## 第六步：报告（中文，必须含这五项）

1. **编号与类型** —— `新文章 #N <slug>` 或 `更正 #N <slug>`
2. **这一轮做了什么**，含实测数字（闸门几过、改了哪些文件、reviewer 几条）

**一行格式**：`第 N 篇已提交 · 闸门 X/Y · 成本 ¥Z · 缺：<一句话>`

## 出错时

**任何一步失败，不要跳过、不要假装成功。** 把失败原因和你的判断写进报告，然后停下。

**但不要为了让报告好看而绕过闸门。** 一道闸门红了就是红了——那是它在工作，不是它在碍事。

**也不要为了修那两项沙箱限制反复尝试**——它们是宿主级设置，从仓库里改不了，而包装脚本已经替你做了那两件事。
