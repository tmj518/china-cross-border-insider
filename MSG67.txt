fix: the 08:10 run died because a Chinese filename inside the script decoded as GBK

The scheduled task ran this morning and failed immediately: Last Result 2, an
eight-line log, and "task file not found at ...\鑷姩鍖朹姣忔棩浠诲姟.txt". Two causes
stacked.

tools/run-daily.ps1 had lost its UTF-8 BOM - my own edit tool removed it the last time
I touched the file - and the script body hardcoded the Chinese filename
自动化_每日任务.txt. Without the BOM, Windows PowerShell 5.1 decodes the script as GBK on
this locale, so the embedded filename became mojibake and the file could not be found.

The instructive part is that running it by hand worked and Task Scheduler did not. Same
file, same machine, same bytes; the two entry points decode it differently. That is why
the fix is not "remember the BOM" - a BOM can be lost again - but removing the
dependency entirely. Anything Task Scheduler executes must be pure ASCII, comments
included, so no byte's meaning depends on the encoding.

What changed:

  * 自动化_每日任务.txt renamed to daily-task.txt, so the filename is ASCII too.
  * tools/run-daily.ps1 rewritten to contain no character above 0x7e, and its BOM
    restored. The Chinese task text stays Chinese: it lives in its own file and is read
    with an explicit UTF-8 decoding, which is unambiguous.
  * tools/check-preflight.ps1 likewise, and it referenced the old 每日体检.bat which no
    longer exists after an earlier rename; corrected to DailyCheck.bat.
  * Every reference to the old task filename updated across the docs.

Verified by running the wrapper with -PreflightOnly: it now finds daily-task.txt and
reaches preflight, which is where it used to die before the first check.

Recorded in 经验与踩坑记录.md as the sixth encoding failure, with the rule stated as an
invariant rather than a reminder.
